## Architecture Overview

```
                        Clients
                           |
            +--------------+--------------+
            |              |              |
       +----v----+    +---v----+    +----v----+
       |  Node 1  |    |  Node 2  |    |  Node 3  |
       |  Leader  |    | Follower |    | Follower |
       |  P:0-33  |    |  P:0-33  |    |  P:0-33  |
       +----+----+    +---+----+    +----+----+
            |              |              |
       +----v----+    +---v----+    +----v----+
       |  Node 4  |    |  Node 5  |    |  Node 6  |
       | Follower |    | Leader   |    | Follower |
       |  P:0-33  |    |  P:34-66 |    |  P:34-66 |
       +----+----+    +---+----+    +----+----+
            |              |              |
       +----v----+    +---v----+    +----v----+
       |  Node 7  |    |  Node 8  |    |  Node 9  |
       | Follower |    | Follower |    | Leader   |
       |  P:34-66 |    |  P:34-66 |    |  P:67-99 |
       +----+----+    +---+----+    +----+----+
            |              |              |
       +----v----+    +---v----+    +----v----+
       | ...      |    | ...      |    |  Node N  |
       |          |    |          |    | Leader   |
       +----------+    +----------+    | P:67-99  |
                                       +----------+

Each partition (e.g., P:0-33) = Raft group with 3 replicas
Hash space = 2^32 partitions, evenly distributed across nodes
```

Each node is equal — there is no centralized coordinator. The hash ring is divided into a large number of virtual partitions (10,000-100,000) that are mapped to physical nodes. This decouples partition count from node count, allowing smooth rebalancing as nodes join or leave.

### Design Rationale

- **Consistent hashing with virtual partitions**: Partitions are fixed points on a hash ring. When nodes join or leave, only a fraction of partitions need to move (controlled by the number of virtual partitions per node). This minimizes data migration during scaling.
- **Raft per partition**: Each partition is an independent Raft group. This provides linearizable consistency, automatic leader election, and split-brain protection without external coordination (ZooKeeper).
- **LSM-Tree storage**: Sequential writes to a memtable + immutable SSTable files. Writes never rewrite existing data, only append. This is optimal for the write-heavy workload of a key-value store.

## Technology Choices

| Component | Choice | Rationale | Alternatives Considered |
|---|---|---|---|
| **Partitioning** | Consistent hashing with virtual partitions | Smooth rebalancing, O(1) key lookup | Range partitioning (hotspot risk), hash modulo (unbalanced) |
| **Replication** | Raft consensus | Linearizable consistency, no external ZK dependency | Primary-replica (split-brain risk), Paxos (harder to implement) |
| **Storage Engine** | LSM-Tree (memtable + SSTable) | Sequential writes, O(1) write amplification | B-Tree (random writes slow on HDD), log-structured (compaction cost) |
| **In-memory index** | Hash map per SSTable | O(1) key lookup, memory efficient | B-tree index (more complex, not needed for immutable files) |
| **Cache optimization** | Bloom filter per SSTable | Probabilistic skip avoids disk reads for missing keys | Binary search (slower for large SSTables), skip list (more memory) |
| **Network protocol** | gRPC (Protobuf) | Strong typing, streaming, HTTP/2 multiplexing | REST/JSON (slower, larger payload), custom binary (more code to maintain) |

### Why LSM-Tree over B-Tree for a Key-Value Store?

A B-Tree keeps data sorted on disk, so every write requires a random-access read-modify-write on the disk. A key-value store with 100K writes/sec would need 100K random disk IOPS per node — impractical at scale. An LSM-Tree batches writes in memory, then flushes as a sorted SSTable. All reads are:
- Memtable: O(log n) in-memory skip-list traversal
- SSTable: O(1) hash lookup in index block + sequential file read

The tradeoff is write amplification during compaction (multiple SSTable passes), but compaction runs at low I/O priority and is fully sequential, so it does not compete with client latency.
