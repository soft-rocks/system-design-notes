## Sharding Scheme

**Sharding key**: `shard_id = hash(prefix) % 32` (MurmurHash3, 32 shards)

Each shard contains ~300M prefix entries. Despite skew (first character "e" gets ~20% of queries), consistent hashing with virtual nodes (256 vnodes per shard) balances load within ±15%.

**Per-shard capacity**: 250GB (RocksDB engine, AOF persistence, multi-AZ replication). Each shard runs on 4 nodes (1 primary + 3 replicas) for HA.

## Cache Key Design

```
# Global prefix index (shared across all users)
Cache: prefix:\{prefix\} → sorted_set \{("google", 98.5), ("google maps", 92.1), ...\}

# Per-user context (for personalization)
Cache: user:\{userId\}:context → hash \{last_queries: ["...", "..."], location: {...\\&#125;&#125; 

# Rate limiting
Cache: ratelimit:ip:\{ip_hash\} → sorted_set \{timestamp → 1\}
Cache: ratelimit:user:\{user_id\} → sorted_set \{timestamp → 1\}
```

### Sorted Set Cardinality: Top-K per Prefix, Not All Terms

Each `prefix:\{p\}` key stores **only the top-50 terms for that prefix**, not all matching terms. This is critical:

- 10 billion terms × avg 4 prefix chars = 40 billion prefix-term pairs → far too large for sorted sets
- But most queries are short (2-3 chars), and only the top-50 per prefix are returned
- During dictionary build, only the top-50 terms per prefix are added to the sorted set
- This keeps each sorted set small (~50 members) and each shard manageable

```
# What's in the cache:
prefix:go → ZSET [("google", 98.5), ("google maps", 92.1), ("golang", 89.0), ...]  // top 50

# What's NOT in the cache:
prefix:go → ZSET [("gopher", 0.001), ("goreview", 0.0001), ...]  // long-tail, not top 50
```

Terms outside top-50 can still appear if the user query is long enough to be specific (4-5 characters), but they are rare and typically replaced by the next dictionary rebuild cycle.

## Cache Invalidation & Updates

**Write pattern**: Push-based from dictionary builder service, not read-through.

- Dictionary builder pushes batched updates every 5 minutes to cache shards via `ZADD` commands
- Each update includes: `prefix`, `term`, `new_score`, `new_category`
- **Conditional updates**: only write if `abs(new_score - old_score) > 20%` or `usageCount` exceeds threshold
- This reduces write volume by ~60% — most terms have stable scores

### Term Expiration: Background Aging Scan (Not TTL)

**Why no per-entry TTL**: TTL on individual entries doesn't capture the concept of "24 hours of silence." A term typed once at midnight and never again should be expired, but TTL doesn't know about usage patterns.

**Solution: background aging scan running every 10 minutes**:
1. Scan all `prefix:*` sorted sets (parallelized across shards)
2. For each term, check `lastUsed` timestamp
3. If `now() - lastUsed > 24h`, remove from sorted set via `ZREM`
4. If a sorted set becomes empty, delete the key

**Optimization**: The scan is incremental — it only processes keys that changed in the last 10 minutes (tracked via a bloom filter per shard). This avoids scanning the entire 300M-key namespace every cycle.

## Capacity Management

| Watermark | Action |
|-----------|--------|
| 70% | Normal operation, no action needed |
| 80% | Begin gradual eviction of lowest-score terms (~100K entries/minute) |
| 85% | Aggressive eviction across all shards; skip conditional update checks |
| 90% | Reject new dictionary builder updates; prioritize read traffic |

Evicted terms re-appear when they re-enter the trending window (next dictionary rebuild cycle adds them back if their score is high enough).

## Cache Warming on Restart

When a shard restarts (crash, deployment, or scaling event):

1. **Phase 1** (0-30s): Load RocksDB snapshot from disk (~30 seconds for 250GB)
2. **Phase 2** (30-40s): Replay delta log (WAL replay of 5 minutes of changes)
3. **Phase 3** (40-45s): Load user context cache from Redis replication peer
4. **Phase 4** (45-60s): Warm trending cache with 7-day rolling baseline from Flink checkpoint

During phases 1-3, requests to this shard are routed to the consistent hash neighbor. Users see fewer suggestions but no errors.

## Cache Consistency During Rolling Deployments

**Suggest Service rolling deploy** (zero-downtime):
1. Dequeue one instance from Envoy load balancer
2. Wait for active connections to drain (30s)
3. Deploy and start (10s)
4. Add back to load balancer
5. Proceed to next instance

**Cache shard rolling deploy** (requires care):
1. Remove shard from consistent hash ring (clients route to neighbors)
2. Stop old instance, start new instance
3. Wait for snapshot load + WAL replay (~40s)
4. Add shard back to ring
5. Proceed to next replica

**Key rule**: Never have fewer than 3 replicas per shard during deployment. This ensures that even with one shard down, the consistent hash ring can redistribute load without overwhelming any single neighbor.

## Cache Failure Handling

### Scenario 1: Single shard down (Redis crash)
- Client request routes to next consistent hash neighbor
- Missing results are acceptable — user sees fewer suggestions but no error
- Shard rebuilds from disk (RocksDB snapshot + WAL: ~40 seconds)

### Scenario 2: Shard slow (>15ms p99)
- Circuit breaker in Suggest Service trips after 3 consecutive slow responses
- Request falls back to the next consistent hash neighbor
- Neighbor returns results with ~5ms added latency

### Scenario 3: All shards saturated
- API Gateway enforces rate limiting (5 req/s per IP anonymous, 20 req/s per user)
- Authenticated users get priority — their requests are never throttled under normal load
- Fallback: query Elasticsearch directly for missing prefixes (adds ~5ms, serves as last resort)
