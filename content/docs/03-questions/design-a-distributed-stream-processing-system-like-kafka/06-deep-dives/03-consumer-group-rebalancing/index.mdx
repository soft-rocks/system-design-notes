## Rebalancing Triggers

A rebalance reassigns partition ownership among consumer group members. It is triggered by:

1. **New member joins**: A consumer subscribes to the group.
2. **Member leaves**: A consumer shuts down gracefully (sends LEAVE_GROUP request).
3. **Member dies**: A consumer crashes and its heartbeat times out on the coordinator.
4. **Topic changes**: New partitions are added to a subscribed topic (partition count increase).
5. **Cooperative assignment change**: The assignor logic is updated to a new strategy.

**Why rebalancing is expensive:**

During a rebalance, all consumers in the group stop processing. The coordinator (a designated consumer) computes the new assignment, distributes it, and all consumers commit their current offsets. This "stop-the-world" pause can last from hundreds of milliseconds to several seconds depending on group size and commit latency.

**The cost at scale:**

With 1,000 consumers and 10,000 partitions, a full rebalance stops 1,000 consumers simultaneously. Each rebalance takes ~2 seconds. If consumers frequently join/leave (auto-scaling), the system spends a significant fraction of time rebalancing rather than processing. This motivated the shift from cooperative-eager (stop-the-world) to cooperative-sticky assignment.

## Cooperative Sticky Assignor

The cooperative-sticky assignor (introduced in Kafka 2.0.0) has two key innovations:

**Incremental rebalancing:** Instead of revoking all partitions and redistributing from scratch, the new protocol allows the coordinator to compute only the delta — which partitions move from A to B. Consumers keep their existing partitions unless explicitly told to release them.

**Sticky assignment:** The algorithm tries to keep partition assignments as close to the previous generation as possible. It minimizes the number of partition moves while maintaining balance. This reduces hotspots during rebalancing and gives downstream systems (like local caches) more time to stabilize.

```
Generation 1: [C0: P0,P1,P2] [C1: P3,P4,P5]
C1 leaves → Generation 2: [C0: P0,P1,P2,P3,P4,P5] (C0 takes all)
C1 rejoins → Generation 3: [C0: P0,P1,P2] [C1: P3,P4,P5] (back to original)

With cooperative-sticky: C1 only gets P3,P4,P5 — C0 only releases those partitions.
P0,P1,P2 stay with C0 throughout. No cache invalidation for those partitions.
```

**The rebalance protocol flow:**

```
1. Consumer sends JoinGroup with its current assignment (generation ID + partition list).
2. Coordinator collects from all members, then calls Assignor.rebalance() with the current state.
3. Assignor computes the new assignment, respecting sticky constraints (minimize moves).
4. Coordinator sends JoinGroupResponse with the new assignment.
5. Consumers send SyncGroup with their prepared offset commits.
6. Coordinator distributes the final assignment.
7. Consumers begin processing new partitions.
```

The incremental protocol (KIP-345) adds a `syncGroup` variant that accepts only the changes, skipping the full assignment computation for stable partitions.

## Striped Rebalancing

For very large groups (thousands of consumers), even cooperative rebalancing can be slow because a single coordinator handles all rebalances for the group. Striped rebalancing (KIP-480) partitions the rebalance coordination across multiple coordinators.

**How it works:**

The consumer group is divided into stripes. Each stripe has its own coordinator that handles join/sync for a subset of consumers. Rebalances are localized to the affected stripe — if a consumer in stripe 2 crashes, only stripe 2's coordinator is involved. Other stripes continue processing without interruption.

```
Stripe 0: C0-C99   Coordinator: C10
Stripe 1: C100-C199 Coordinator: C110
Stripe 2: C200-C299 Coordinator: C120

C250 crashes → only stripe 2 rebalances. Stripe 0 and 1 continue processing.
```

**Tradeoffs:**

Striped rebalancing requires the number of consumers to be a multiple of the stripe count, which limits flexibility in group sizing. The assignment is no longer globally optimal — each stripe is balanced independently, which may lead to slight imbalance across stripes. For most systems, cooperative assignment alone is sufficient; striped rebalancing is only needed at very large scale (>1000 consumers per group).
